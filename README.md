# Azure Migration Assistant

A single-user Streamlit app that inspects application and server inventory, estimates Azure Database for PostgreSQL Flexible Server sizing, and provides an offline Db2-to-PostgreSQL assessment intake for DBA-supplied metadata exports. It also has a guided "Research & guide" page that teaches the sizing rules.

## Run it

**Repeatable local run with Docker:** install Docker Desktop, clone this repository, then run:
```bash
docker compose up --build
```
Open `http://localhost:8501`. The image uses the pinned Python dependency set in `requirements-docker.lock`, so teammates run the same app environment. The three Db2 synthetic demos are generated by the app; no Db2 installation is needed to exercise the assessment workflow. Uploaded source exports are processed by the app and are not baked into the image. The named `app_config` volume preserves local path settings between container restarts. Stop with `docker compose down`.

The container does not bundle the ignored `samples/` folder. The Home page can use files uploaded through the UI; to use local sample workbooks inside Docker, mount a reviewed folder into the container deliberately.

**Team members (no Python needed):** download the zip for your OS from the Releases page (or the Actions run), unzip, and run `AzureMigrationAssistant` (`.exe` on Windows). A console window opens and so does your browser. Close the console window to stop.
- macOS: first launch may be blocked. Right-click the file, choose Open, then confirm.
- Windows: SmartScreen may warn about an unsigned app. Choose "More info", then "Run anyway".

**From source:**
```bash
./scripts/run.sh          # creates .venv on first run, then starts the app
```
Opens at `http://localhost:8501`. Supported workbooks in `samples/` are discovered and loaded on startup; use **Load sample files** to load them again.

## Supported source workbooks

The ingestion layer recognizes ServiceNow application inventory, BA-AS-to-server relationships, CMDB server inventory, Axonius device inventory, RVTools exports, Visual Group inventory, and generated sizing reports. It classifies worksheets from their headers, maps recognized fields to canonical application/server fields, and retains other columns as `extra:` fields. The raw explorer shows required-field checks, source lineage, and a session-level field mapping editor for changed or unfamiliar headers. Application IDs and record counts are not fixed.

Hardware lookups join application IDs to server relationships, then match hardware records by FQDN and hostname. The result reports CPU, RAM, allocated and used storage, and the source inventory used for each server. DB2 SQL or catalog compatibility analysis needs DB2 metadata exports; the current workbooks describe applications and infrastructure, not SQL objects or database types.

## Build the executable

PyInstaller builds only for the OS it runs on.

```bash
pip install -r requirements.txt -r requirements-build.txt
python packaging/build.py        # -> dist/AzureMigrationAssistant-<os>.zip
```

For Windows and macOS together, use GitHub Actions: run **Build executables** from the Actions tab, or push a tag (`git tag v1.0.0 && git push --tags`) to attach both zips to a release.

The bundle contains the code, `docs/` and the theme only. Real exports in `samples/` are not included, and each user's saved file paths stay in their own home folder.

## Db2 assessment intake

Open **Db2 assessment** to download the canonical metadata export template. The page accepts DBA-provided metadata for Db2 LUW, Db2 for z/OS, or Db2 for i; it does not connect to source databases. It validates object, column, dependency, and metric exports and reports evidence gaps. This intake milestone does not convert DDL or claim PostgreSQL compatibility. See [the assessment intake contract](docs/db2_assessment_intake.md) for the export fields and platform catalog starting points.

## Azure sizing rules

Rules follow `docs/azure_research.md` (Canada Central, Flexible Server, v5 SKUs):

- **Production:** General Purpose (D-series, 4 GiB/vCore) by default. Memory Optimized (E-series) when the RAM target needs it or the source RAM:vCPU is above 4:1.
- **Non-production:** Burstable, dev/test only. No HA.
- **Advanced inputs:** peak CPU %, hot working set, data growth, peak IOPS and connection counts replace default estimates with your measurements.
- **Storage:** 12 months of growth +30% MVCC/WAL headroom, 32 GiB minimum. IOPS are the lower of the disk's and the VM's limit.
